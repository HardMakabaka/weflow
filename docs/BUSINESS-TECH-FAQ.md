# 支付 / VCC / 收单业务与技术 FAQ

本文从业务相关微信会话中整理，覆盖支付收单、VCC/虚拟卡、API 对接、Webhook、通道、退款拒付、费率结算和联调排障。文档只保留可复用问题和处理口径，聊天中的账号、密钥、订单号、链接、客户资料不写入。

重要原则：先区分“内部平台”和“外部上游”。Spark / SparkHam 是 Fizz-Bolt 的历史命名，和会话里的 Fizzbolt 都按内部平台处理；PayingPays、Conflux、Anton / Antom、VoyaPay、Slash、光子易、Gate 等再按外部上游或通道分别确认。不能把某个外部上游的规则当成全平台通用规则。

## 适用范围

- 代理、商户、通道方、技术联调方之间的支付 / VCC / 收单沟通。
- 支付订单创建、支付跳转、Webhook 回调、退款、拒付、撤销、卡交易、费率、结算相关问题。
- API 联调、测试环境、生产环境、鉴权、签名、请求格式、回调重试相关问题。

## 问题归属索引

### Fizz-Bolt 内部平台（原 Spark / SparkHam / Fizzbolt）

说明：

- Spark / SparkHam 是旧名称，当前统一按 Fizz-Bolt 内部平台处理。
- 会话名里出现的 `Fizzbolt`、`Fizzbolt API 发卡`、`Fizzbolt 运营`、`Spark Card`、`SparkHam VCC` 都归入内部平台范围。
- Fizz-Bolt 内部平台问题要和外部上游问题分开：内部平台负责商户侧 API、VCC / 发卡能力、回调接收与转发、余额台账、预算、报表、费率配置和客户可见状态；外部上游负责各自的通道能力、回调 payload、结算、拒付、手续费、白名单和审核。

主要问题：

- VCC / 共享虚拟卡 / 发卡 API。
- Webhook 订阅、接收、转发、成功响应格式、重复发送处理。
- Webhook 文档缺字段，尤其交易更新、授权、清算、退款、撤销、拒付阶段。
- 交易记录是否拆分授权和清算。
- 两要素、三要素、3DS / OTP、授权成功但无法扣款。
- 卡冻结、停用、注销、删卡、预算删除后的退款 / 撤销归集。
- 共享卡跨境交易手续费、最低收费、撤销费率、卡头费率。
- 上游非卡内余额、上游充值到账、客户预算入账、内部余额台账核对。

处理口径：

- 只要问题发生在 Spark / SparkHam / Fizzbolt 相关会话里，先按 Fizz-Bolt 内部平台排查，再定位具体外部上游或卡头。
- Webhook 成功响应、重试规则、交易事件 payload 需要区分：内部平台对商户的文档，以及外部上游给内部平台的文档。
- 卡生命周期和资金归集规则必须按内部平台、卡头、预算体系和外部上游规则一起确认。
- VoyaPay、Slash、大金鸟等是外部上游或余额来源，不是 Fizz-Bolt 的历史名称。

### PayingPays / A-JANE Trading

主要问题：

- Cash、ApplePay、GooglePay 产品联调。
- `/pl/pay/getPrepaidOrders` 创建预付订单。
- `redirectAddress` 带参数后无法支付。
- 白名单审核、测试商户、Gateway URL、测试卡能力。
- 支付页面显示成功但商户订单未变更为已支付。
- Webhook 是否发送、发送到哪里、支付成功 / 失败 / 退款 / 拒付事件是否完整。
- JSON 请求体格式错误，例如多余逗号导致解析失败。

处理口径：

- 该上游的测试 / 生产可能通过商户和凭证区分，不一定通过不同 URL 区分。
- GooglePay 可用测试卡验证；ApplePay 是否需要生产环境，应按该上游当前配置确认。
- `redirectAddress` 的白名单匹配和 query 参数支持，需要单独向该上游确认，不能套用到其他上游。

### Conflux / Tech Nova

主要问题：

- Cash、wallet、ApplePay、GooglePay 配置和密钥区分。
- 测试环境与生产环境隔离，生产会下发新的配置和生产 URL。
- 退款 Webhook：聊天中出现过“API 退款有回调，后台直接发起的退款暂未做回调”的口径。
- 批量查询订单接口缺失，定时同步只能单笔查询时效率较低。
- 成功率、拒付率异常，需要结合其他 Cash 客户数据对比。
- Cash 单笔底价、T+4 结算等报价和结算条件。

处理口径：

- Conflux 相关回调问题要先区分 API 发起还是后台发起。
- Cash、wallet 可能是两套密钥，不能混用。
- GooglePay 临时关闭、ApplePay/Cash 可用等状态要按当时配置确认。

### Anton / Antom 通道

主要问题：

- 收单代理账号已开通，但通道仍需另行分配。
- Anton 通道配置等待、审核站点异常、可分配通道是否可用。
- Anton / Antom 的成本费率、代理费率、审核站、商户应跑哪条通道。
- Antom 交易手续费是否退回。

处理口径：

- “代理账号开通”不代表 Anton 通道已配置完成。
- Anton / Antom 的退款费、拒付费、交易手续费退还、审核站点都要单独确认。
- 如果审核站点异常，应建议先看其他渠道，不能承诺固定上线时间。

### VoyaPay / Slash / 大金鸟等外部余额来源

主要问题：

- VoyaPay、Slash、大金鸟等上游非卡内余额跟踪。
- 上游充值是否到账、到账后是否已充值到客户预算。
- 外部余额与 Fizz-Bolt 内部预算、钱包、卡内余额之间的核对。

处理口径：

- 余额问题必须区分上游非卡内余额、卡内余额、客户预算、钱包余额。
- Slash、VoyaPay、大金鸟等上游余额不要合并成一个“上游余额”。
- 充值到账后是否进入客户预算，需要逐笔核对。

### 光子易 / PhotonPay

主要问题：

- 测试环境商户后台、API 文档、指南文档。
- 测试环境 IP 白名单。
- 测试环境中需要短信验证码验证的功能。
- 生产账号在客户侧，测试操作和生产操作类似但凭证不同。
- 通知验签和 token 获取机制。

处理口径：

- IP 白名单是光子易测试环境的关键前置条件，不应当成所有上游都要求固定 IP。
- 验签、token 机制需要按光子易文档确认，不能要求对方提供源码作为常规方案。

### Gate

主要问题：

- 人工清算退款、商户清退、账单对账。
- 登录 Gate 需要邮箱验证码或 Google 验证码。
- 下发退款或转账前要确认钱包余额、操作权限和 2FA。

处理口径：

- Gate 更偏后台资金操作和对账，不等同于支付收单接口上游。
- 涉及验证码和人工下发时，必须留操作记录，避免只在聊天里完成确认。

### YouCard / Lapay

当前会话中只有少量接入线索：

- YouCard：出现过是否接入虚拟卡通道、API 文档文件。
- Lapay：出现过收单合作群，但尚未看到可复用业务规则。

处理口径：

- 这两类暂不沉淀具体业务规则，只放入待跟进上游。
- 后续拿到 API 文档、费率、回调、结算规则后再补充。

## 业务 FAQ

### 1. 代理账号显示收单功能已开通，为什么还不能直接跑量？

收单功能开通不等于已经分配可用通道。业务上至少要同时满足：

1. 代理账号 / 商户账号可用。
2. 有可分配的上游通道。
3. 通道审核、站点配置、白名单或商户资料已通过。
4. 费率、结算、保证金、退款 / 拒付规则已确认。

如果上游通道审核站点异常，或当前没有可分配通道，应先切换其他渠道或等待通道恢复，不要把“账号开通”理解为“通道已可交易”。

问题归属：该问题在 Fizz-Bolt 内部代理对接流程、Anton 外部通道相关沟通中最明显；其他外部上游也可能存在类似情况，但不能直接套用 Anton 的审核状态。

### 2. 通道审核或站点出问题时怎么处理？

先确认问题发生在账号、通道还是站点审核环节。若是上游审核站点问题，应对外说明“通道审核暂不可完成”，并给出替代渠道或预计跟进时间。内部需要记录：通道名称、商户主体、审核节点、当前阻塞原因、下一次跟进人。

问题归属：Anton 通道出现过审核站点异常；Conflux 出现过审核站信息未给齐；光子易测试环境出现过 IP 白名单前置条件。三者不是同一个问题。

### 3. 测试商户和生产商户怎么区分？

部分上游不是通过不同 Gateway URL 区分测试 / 生产，而是通过商户号、AppId、API Key 或产品配置区分。接入时不要只看 URL，要核对当前凭证属于测试商户还是生产商户。

生产账号在客户或通道方侧时，测试流程可以一致，但生产凭证、生产风控、可用支付方式可能不同。

问题归属：PayingPays 会话里出现过通过商户区分测试；Conflux 明确出现过生产和沙盒隔离、生产下发新配置和生产 URL；光子易是测试环境后台和 IP 白名单。

### 4. GooglePay、ApplePay、Cash 的测试能力有什么差异？

PayingPays 会话里出现的口径是：GooglePay 可使用测试卡验证；ApplePay 需要到生产环境才能完整验证。Conflux 会话里出现过 ApplePay 和 Cash 可用、GooglePay 临时关闭。Cash、ApplePay、GooglePay 可能是不同产品配置，不应只用一个产品的测试结果推断另一个产品一定可用。

联调前应确认：

- 当前商户开通了哪些产品。
- 每个产品是否支持沙箱测试。
- 测试卡、真实卡、钱包支付的限制是否不同。
- 某些支付方式是否临时关闭。

### 5. 支付页面显示成功，但商户订单没有变为已支付，怎么处理？

优先按回调链路排查，不要只看前端支付页结果。

1. 查上游是否生成支付成功事件。
2. 查 Webhook 是否已发送。
3. 查 Webhook 是否发送到正确地址。
4. 查商户系统是否收到请求并返回成功响应。
5. 查商户系统是否按商户订单号 / 上游订单号正确更新状态。

PayingPays 会话里出现过“上游配置未打开，重新付款后可以收到通知”的情况。因此遇到该上游同类问题时，应把“上游回调配置是否开启”列为第一批检查项。

问题归属：PayingPays 重点查回调配置和订单状态同步；Conflux 重点区分 API 退款回调和后台退款回调；Fizz-Bolt 内部平台重点查 VCC 交易事件、内部回调转发和商户侧回调文档。

### 6. Webhook 事件应该覆盖哪些业务状态？

支付收单侧至少要按上游确认这些事件是否支持：

- 支付成功
- 支付失败
- 退款
- 拒付 / 争议

VCC / 虚拟卡侧还需要确认卡交易事件，例如授权、清算、撤销、退款、拒付、交易更新等。若上游只给单一交易更新时间，无法区分授权、清算、退款、撤销阶段，后续对账和账务解释会很困难。

问题归属：PayingPays 重点确认支付成功、失败、退款、拒付四类事件；Conflux 已出现“API 退款有回调，后台退款暂未做回调”的差异；Fizz-Bolt 内部平台重点补齐对商户侧输出的交易更新事件和授权 / 清算 / 退款 / 撤销 / 拒付字段。

### 7. Webhook 没收到时，业务上怎么对外回复？

可按以下口径回复：

> 我们先核对上游是否已发送回调，以及回调发送到哪个地址。请提供商户订单号、上游订单号、支付时间、回调地址和当前商户系统状态。若上游配置未开启或回调发送失败，需要修复配置后重新发起交易验证。

不要只回复“没收到”。必须明确下一步需要谁查、查哪个订单、查哪个回调地址、是否需要重新支付或补发回调。

### 8. 退款、撤销或拒付发生时，钱退到哪里？

当前可确认的口径：

- 若退款记录存在，可以通过记录追踪退款。
- 若卡和预算组已被删除，Fizz-Bolt / 共享卡相关沟通里出现过“可手动添加到钱包”的处理方式。
- 手续费、交易费是否退回，取决于上游和通道规则；有会话提到某些上游不退交易手续费。

待确认的口径：

- 卡已删但预算未删时，撤销 / 退款是否自动退回预算。
- 卡和预算都存在时，退款是否一定回原预算或原卡。
- 不同上游的退款手续费、拒付费、撤销费是否有统一配置入口。

问题归属：卡、预算、共享卡相关问题主要归 Fizz-Bolt 内部平台 / VCC；Antom 出现过交易手续费是否退回的问题；Gate 是人工清算退款和下发，不应与自动退款回调混为一类。

### 9. 冻结、停用、注销、删卡是不是一回事？

不是。当前会话里反复出现“冻结后仍产生授权被拒记录”“注销是不是删卡”“停用是不是冻结”等问题，主要归 Fizz-Bolt 内部平台 / 共享卡 / VCC 生命周期，说明这些状态需要产品和运营统一定义。

建议统一口径：

- 冻结：卡不可继续新交易，但历史授权、撤销、退款、拒付仍可能发生。
- 停用：是否等同冻结需要按系统实际定义确认。
- 注销 / 删卡：通常比冻结更强，可能影响后续退款、撤销、预算归集和客户自助操作。
- 预算删除：可能联动预算下卡片或卡段，需单独确认。

对客户解释时，不要把这些词混用。涉及资金回退、授权被拒率、拒付率或手续费时，必须先确认具体状态。

### 10. 卡冻结后产生授权被拒记录，是否会产生费用或影响拒付率？

聊天里出现过客户对此有异议：卡被冻结后仍有授权被拒记录，并可能影响费用或拒付率。该问题主要归 Fizz-Bolt 内部平台 / 共享卡 / 卡头规则，需要按内部配置和外部上游规则共同确认。

建议处理方式：

1. 查该卡冻结时间。
2. 查授权请求发生时间。
3. 查拒绝原因是余额、冻结、风控、3DS、商户限制还是卡状态。
4. 查拒绝记录是否计入客户费用、拒付率或风控指标。
5. 若计费或指标有争议，按通道规则给出书面解释。

### 11. 共享卡跨境交易手续费、撤销费率、返点在哪里配置？

会话中出现过这些问题，主要归 Fizz-Bolt 内部平台 / 共享卡 / 卡头费率，也可能影响 VCC 代理报价：

- 跨境交易手续费按比例计算，但可能有最低收费。
- 撤销费率百分比配置疑似未生效。
- 返点配置位置不清楚。
- 费率需要按卡头 / 通道 / 商户配置确认。

建议把费率来源统一成三层：

1. 商户费率：商户或代理对外报价。
2. 通道成本：上游通道真实成本、汇损、拒付费、退款费。
3. 卡头费率：虚拟卡卡头或 BIN 维度的交易、跨境、撤销、退款规则。

对外报价前，先确认这三层是否都已配置，并检查最终交易记录是否按同一口径计算。

### 12. 退款费、拒付费、结算周期、保证金能否固定写死？

不能。聊天里出现过不同口径，例如退款费、拒付费、T+4 结算、保证金比例和冻结天数等，但这些更像上游 / 通道 / 商户级报价，不应写成全局规则。

FAQ 对外只能写：

- 退款费、拒付费、结算周期、保证金按商户签约通道为准。
- 报价前必须确认通道、币种、交易类型、拒付规则、保证金周期。
- 若页面或合同显示与口头报价不一致，以合同 / 后台配置 / 财务确认为准。

问题归属：Conflux 出现过 Cash 底价、T+4 结算、保证金；Anton 出现过成本费率和代理费率待确认；Fizz-Bolt / 共享卡出现过跨境手续费、撤销费率、卡头费率；Antom 出现过交易手续费是否退回。

### 13. 虚拟卡充值成本是否要计入入金成本？

有会话提到“实际业务要求把虚拟卡充值成本加到入金成本内”。这属于财务核算口径，不只是技术展示问题。

建议规则：

- 若充值成本是完成入金必需成本，应计入入金成本。
- 若成本只发生在卡交易或卡充值环节，应和入金本金、通道手续费、汇损分开记录。
- 报表上至少区分：入金本金、充值成本、通道成本、汇损、返点、保证金。

问题归属：该问题来自 Fizz-Bolt 内部 VCC / 虚拟卡充值成本口径，不能直接套到 Cash 收单、Gate 人工下发或 Conflux Cash 交易。

### 14. 上游非卡内余额和卡内余额要分开看吗？

要分开。Fizz-Bolt 内部余额台账与 VoyaPay / Slash / 大金鸟等外部余额来源相关会话中多次出现“上游非卡内余额”，说明业务上存在卡内余额、上游账户余额、钱包余额、保证金或待结算余额等不同资金池。

排查余额问题时先确认余额类型，不要只问“还剩多少钱”：

- 钱包余额
- 卡内余额
- 预算余额
- 上游非卡内余额
- 待结算
- 保证金
- 冻结金额

### 15. 清算退款或人工下发需要哪些前置条件？

Gate 会话里出现过人工下发退款需要 Google 验证码的情况。涉及人工清算、退款下发、钱包补款时，应提前确认：

- 操作账号是否可登录。
- 是否需要 2FA / Google Authenticator。
- 当前余额是否足够。
- 操作是否会产生手续费。
- 操作完成后在哪里留痕。

## 技术 FAQ

### 16. 创建支付订单时应该调用哪个接口？

PayingPays 会话里提到商户对应接口为 `/pl/pay/getPrepaidOrders`。这不是全平台统一接口。接入时应以对应上游最新开发文档为准，并确认该接口适用于当前商户、产品和支付方式。

最小请求检查项：

- Merchant / AppId / API Key 是否匹配当前环境。
- `amount` 单位是否正确。
- `orderNo` 是否唯一。
- `notifyUrl` 是否可公网访问。
- `redirectAddress` 是否符合白名单和编码规则。
- `timestamp` 是否符合上游要求。
- 签名或 Authorization 是否按文档生成。

### 17. 返回 `illegal input` 或 `fastjson` 解析错误，通常是什么问题？

PayingPays 联调里出现过 JSON 中多了一个逗号导致解析失败的情况。此类错误优先按请求体格式处理，不要先怀疑业务逻辑。

处理步骤：

1. 将请求体复制到 JSON 校验器。
2. 检查多余逗号、缺失引号、非法转义、空字段。
3. 确认 `Content-Type: application/json`。
4. 确认签名使用的原文和实际发送的 body 一致。
5. 修复后用同一个订单重新发起测试。

### 18. `redirectAddress` 带后缀参数后无法支付，怎么排查？

PayingPays 会话中出现过“redirectAddress 带不同后缀参数后无法支付，不带参数与白名单一致”的问题。该问题先按 PayingPays 白名单 / URL 编码规则处理，不能直接推断其他上游也不支持 query 参数。可能原因包括：

- 上游白名单按完整 URL 匹配，带 query 后不匹配。
- URL 未编码，特殊字符破坏请求体或签名。
- 上游不支持动态 query 参数。
- 回跳地址长度或字符集超限。

建议处理：

1. 先用完全白名单一致的回跳地址验证支付。
2. 将业务参数放到订单号、merchantReference、state 或服务端映射表中。
3. 若必须放 query，确认上游白名单是否支持域名级、路径级或通配匹配。
4. 对 URL 做标准编码，并确认签名原文一致。

### 19. Webhook 重复发送，接收方要返回什么？

Fizz-Bolt API 发卡会话中有明确问题：“Webhook 要返回什么才不会重复发送”，说明 Fizz-Bolt 内部 API 文档需要补充。外部上游也要分别确认，不能把内部平台对商户的成功响应格式当成所有外部上游的通用规则。

在未拿到上游明确规则前，接收方应至少做到：

- HTTP 状态码返回 2xx。
- 响应体使用上游要求的成功格式。
- 处理逻辑幂等，按事件 ID、上游订单号、交易 ID 或商户订单号去重。
- 先落库再返回成功，避免处理失败但上游停止重试。

待确认：具体返回 `1`、`success`、JSON 成功体还是仅 2xx 即可，需要上游文档明确。

### 20. Webhook 文档缺哪些字段？

Fizz-Bolt / VCC / 虚拟卡交易回调至少需要明确：

- 事件类型，例如 `transaction.update`。
- 卡号是否脱敏。
- 交易 ID、交易组 ID、商户名称、交易金额、币种。
- 授权时间、拒绝时间、清算时间、退款时间、撤销时间。
- 当前交易状态与上一状态。
- 签名字段和验签方式。
- 重试规则和成功响应格式。

如果只提供单一 `created_at` / `updated_at`，很难解释授权、清算、撤销、退款、拒付之间的生命周期。

### 21. 401 是业务失败还是鉴权失败？

401 通常说明请求还没有进入业务处理阶段。Fizz-Bolt API 发卡会话中出现过“401 还没有到业务处理”的排查结论。外部上游也通常类似，但仍要以各自鉴权规则为准。

排查顺序：

1. Authorization / Token / API Key 是否正确。
2. 签名算法、签名字段、大小写、排序是否正确。
3. 时间戳是否过期。
4. 当前凭证是否属于这个商户或产品。
5. IP 白名单是否生效。

不要在 401 时优先排查订单、余额或通道，因为请求可能还未进入这些逻辑。

### 22. 测试环境报错，是服务器问题还是网络 / IP 问题？

PayingPays 测试联调中出现过“切换到国外 IP”的处理建议；光子易测试环境出现过 IP 白名单前置条件。遇到测试环境偶发不可支付、页面打不开、请求异常时，应区分：

- 请求体错误。
- 鉴权错误。
- 商户 / 产品未开通。
- IP、地区、白名单限制。
- 上游测试环境不稳定。

建议保留一次完整请求日志，包括时间、请求 ID、商户、产品、支付方式、IP 区域、HTTP 状态码和上游响应。

### 23. ApplePay / GooglePay / Cash 是否能用同一套测试结论？

不能。不同产品可能有不同环境、不同可用支付工具和不同风控。PayingPays 出现过 GooglePay 可测试、ApplePay 需要生产；Conflux 出现过 ApplePay/Cash 可用、GooglePay 临时关闭。

验收时应按产品分别验证：

- 订单创建。
- 支付页打开。
- 支付成功。
- Webhook 成功。
- 支付失败。
- 退款。
- 拒付 / 争议。

### 24. 授权成功、清算成功、扣款成功是否等价？

不等价。Fizz-Bolt / VCC 会话里出现过两要素、三要素、3DS、授权成功但无法扣款等问题。

技术上应拆分：

- Authorization：授权。
- Clearing / Settlement：清算或结算。
- Reversal：撤销。
- Refund：退款。
- Dispute / Chargeback：争议或拒付。

对外状态不要只写“成功”。应明确成功的是授权、支付、清算、退款还是拒付处理。

### 25. 为什么需要把授权 / 清算流水拆分？

如果授权和清算共用一条流水，后续会难以回答：

- 什么时候首次授权。
- 什么时候被拒。
- 什么时候清算。
- 什么时候退款。
- 什么时候撤销。
- 什么时候拒付。

建议交易记录至少支持增量状态变更，或在同一记录内提供上述阶段时间字段。

问题归属：该问题主要来自 Fizz-Bolt / VCC 交易记录改造诉求；Conflux 和 PayingPays 是否需要同样拆分，要按各自订单和交易模型确认。

### 26. 平台是否应该把上游信息直接暴露给商户？

不建议。Conflux 相关沟通里出现过“上游信息对外暴露”的担忧。更稳妥的方式是：

- 平台对商户提供统一 API、统一鉴权、统一错误码。
- 内部自行映射不同上游通道、AppId、API Key 和产品配置。
- 对外文档只暴露平台需要商户知道的字段。
- 排查时内部日志保留上游请求 ID 和映射关系。

### 27. 对接时最小日志应该记录什么？

为了支持支付、回调、退款、拒付排查，至少记录以下字段。字段要按归属补充：PayingPays 重点保留预付订单和回跳链路；Conflux 重点保留 Cash/wallet 产品和退款来源；Fizz-Bolt 内部平台重点保留卡交易生命周期；Gate 重点保留人工操作记录。

- 商户订单号。
- 上游订单号。
- 请求时间和响应时间。
- 产品类型和支付方式。
- 请求状态码和错误码。
- Webhook 接收时间、事件类型、签名校验结果。
- 幂等处理结果。
- 资金状态：授权、清算、退款、撤销、拒付。

不要记录明文密码、完整卡号、完整 Token 或完整 Authorization。

### 28. 接入文档里出现账号、密码、AppSecret 怎么处理？

PayingPays、Conflux、光子易等会话中都出现过测试账号、密码、AppSecret、API Key 或验证码类信息。正式文档不要写入真实密钥。建议：

- 示例使用 `<APP_ID>`、`<API_KEY>`、`<APP_SECRET>`、`<TOKEN>`。
- 已在群聊中明文发送过的测试密钥，应视为已泄露并尽快轮换。
- 生产密钥只通过安全渠道交付。
- 文档中只保留字段说明和生成方式。

### 29. 联调验收不能只测支付成功，还要测什么？

至少覆盖以下场景。不同归属要分开验收，不要用 PayingPays 的支付成功覆盖 Fizz-Bolt 的卡交易，也不要用 Conflux 的 Cash 测试覆盖 ApplePay/GooglePay：

1. 创建订单成功。
2. 创建订单失败。
3. 支付页正常打开。
4. 支付成功回调。
5. 支付失败回调。
6. Webhook 重试和幂等。
7. 退款。
8. 撤销。
9. 拒付 / 争议。
10. 卡冻结 / 停用 / 删除后的交易行为。
11. 费率、手续费、汇损、返点计算。
12. 结算、保证金、钱包或预算余额变化。

### 30. 出现问题时应该让对方提供哪些信息？

统一收集这些信息，并增加“归属类型 / 外部上游 / 内部平台”作为必填项：

- 商户名称或商户号。
- 归属类型：内部平台、外部上游、通道、后台资金操作。
- 内部平台：Fizz-Bolt（原 Spark / SparkHam，会话里可能写作 Fizzbolt）。
- 外部上游 / 通道：PayingPays、Conflux、Anton / Antom、VoyaPay、Slash、光子易等。
- 后台资金操作：Gate 等。
- 产品类型：Cash、ApplePay、GooglePay、VCC、虚拟卡等。
- 环境：测试或生产。
- 商户订单号。
- 上游订单号或交易 ID。
- 请求时间。
- HTTP 状态码和错误码。
- 回调地址。
- 当前订单状态。
- 是否发生退款、撤销、拒付或冻结。
- 相关截图或日志，但不要发送完整密钥、完整卡号、完整 Authorization。
